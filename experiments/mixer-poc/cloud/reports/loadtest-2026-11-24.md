# Cloud load test, 2026-11-24

400 simulated phones followed the public feed while a scripted show played 3 rounds × 30 songs (a landing every 500 ms) through the real laptop link into the Worker under `wrangler dev` (workerd, the real wrangler.jsonc). In round 2 every phone dropped at once and came back with the app's jittered backoff. Produced by `npm run loadtest` (loadtest/run.ts); the projection model is loadtest/model.ts.

## What happened

| | |
|---|---|
| Phones that ended with exactly the cloud's public state | **400 / 400** |
| Gaps seen by phones (a delta out of order → resync) | 0 |
| Phone connections (first + after the storm) | 800 (GameRoom accepted 800) |
| Storm: every phone back after | 1.3 s, reconnections spread over 0.9 s |
| Landing → phone (local machine) | median 14 ms, p95 31 ms, max 63 ms |
| Journal entries in the cloud | 134 of 134 (104 uploads, 0 duplicates, 0 conflicts, 0 refused) |
| Messages from the laptop | 385 (4.3 per song) |
| Messages from phones | 0 |
| Messages to phones | 81306 (203 broadcasts) |
| SQLite rows written / read | 344 / 209 (3.82 written per song) |
| Data per phone | 37.6 KB for 90 songs; the full public state is 5.1 KB |

## A show night against the Free plan (per day, resetting 00:00 UTC)

Assumptions: 400 phones, 4 h of show, 12 rounds × 45 songs, each phone reconnecting 12 times an hour (screen locks, network changes; worst case 30), 200 admin API calls, plus a same-day rehearsal of 20 phones for 2 h. The per-song costs are the measured ones above.

| Limit | Free plan | Show night | Worst case | Used (worst) |
|---|---|---|---|---|
| Worker requests | 100,000 | 20,350 | 49,870 | 49.9% |
| Durable Object requests | 100,000 | 20,971 | 50,491 | 50.5% |
| Duration (GB-s) | 13,000 | 31 | 692 | 5.3% |
| SQLite rows written | 100,000 | 2,840 | 5,680 | 5.7% |
| SQLite rows read | 5,000,000 | 44,920 | 74,440 | 1.5% |

- Phone connections dominate: 20,150 on a typical night. The requests limit is reached only if every phone reconnects about 60 times an hour (once every 1.0 min) for the whole night.
- The laptop sends 4.3 messages per song (journal uploads, Spin events, at most 4 states a second), so 3,775 messages, billed as 189 requests. Phones send nothing.
- Each phone downloads about 226 KB of live updates over the night, plus one snapshot per reconnection (about 31 KB by the last round), so about 966 KB in all on a typical night. Outgoing messages are free.
- Duration assumes 10 ms of activity per event (100 ms pessimistic) and that idle time costs nothing (Hibernation API, no timers in the GameRoom).
- If a limit is hit anyway, only phones and remote consoles stop until 00:00 UTC (01:00 in Catalonia in winter); the show itself never depends on the cloud (ADR 0003). The fix on the spot is the Workers Paid plan (5 USD/month), see docs/deploy-plan.md.

Free plan limits as published by Cloudflare (Durable Objects pricing and Workers limits pages, read 2026-11-24): Workers 100,000 requests/day; Durable Objects 100,000 requests/day, 13,000 GB-s/day (128 MB per object, billed only while not idle under the Hibernation API), 5 million SQLite rows read/day, 100,000 rows written/day, 5 GB stored. A WebSocket connection is one request; incoming WebSocket messages are billed 20:1, outgoing ones are free; each RPC call is one request; each alarm is one request and each setAlarm() one row written. Static assets are free and unlimited.
