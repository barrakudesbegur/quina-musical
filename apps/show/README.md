# The show: land every hook as the drum stops

This year's show app: the sound engine, the show page and the relay. It started as the mixer proof of concept, built from [`docs/research/reports/Bingo DJ mixer research.md`](../../docs/research/reports/Bingo%20DJ%20mixer%20research.md) and, where they differ, the design decisions in [`docs/mixer-design-decisions.md`](../../docs/mixer-design-decisions.md), [`GLOSSARY.md`](../../GLOSSARY.md) and [`docs/adr/`](../../docs/adr/). Built so far:
- the analysis (M0);
- the show engine with the full effects layer (M1 + M2);
- the show state machine: Pace and auto-advance, Hold and Hold music, Back as undo, and the Phase from the cards in play;
- the tablet remote. When Next is pressed, the planner picks a landing time **T** 5–11 s ahead on one of the outgoing song's downbeats. It schedules A's exit and B's start so that B's hook downbeat sounds exactly at T, and it solves the drum's physics so the wheel locks on B's card at that same instant.

## Run it

```sh
cd apps/show
npm install                       # Node ≥ 23.6 (type stripping): Vite, Svelte, TypeScript, ws
npm run prep                      # prepare the default repertoire: covers, decode, analysis, Check snippets, report, keys, stems, Signatures, and the Interval playlist
npm run dev                       # relay + Vite on http://localhost:5174, this laptop only (a manual reload picks up edits)
```

For a show, run the built pages instead: `npm start` builds them and serves `dist/`. The relay with `--dist` refuses a `dist/` built from other sources than the checkout's (`dist/build.json`, relay/build-stamp.ts), so a stale build never reaches the night. Add `-- --lan` so the hotspot's tablets and phones can connect. They pair with the relay token in the LAN URL the relay prints (`?t=…`, see docs/protocol.md › Relay).

The Python venvs (never `/usr/bin/python3`, it is 3.9):
- `uv venv --python /opt/homebrew/bin/python3.13 tools/prep/.venv && uv pip install --python tools/prep/.venv/bin/python -r tools/prep/requirements-layering.txt -r tools/prep/requirements-test.txt` (from the repo root) (the analysis, keys and tests);
- `tools/prep/.venv-stems` for Demucs, set up as `tools/prep/requirements-stems.txt` says.

**Repertoires.** A Repertoire (GLOSSARY, D178) is an edition's prepared songs, all prepared together: it holds the edition's pools (Pool 1, Pool 2), each song tagged with its `pool`. Ids are unique within a repertoire and restart at 1 in every repertoire, so each repertoire keeps its own outputs. `data/repertoires/<name>.json` describes one. `default` is last year's 77 songs: test material, whose outputs stay where they always were (`data/out/`, `data/cache/`, `data/repertoires/default/overrides/`). Every repertoire-specific script, `prepare.py` and the relay take `--repertoire <name|path>`; without it, `$QUINA_REPERTOIRE`, then `default`. Hold music (`data/out/hold/`, `data/cache/hold/`) and the Interval playlist (`data/out/interval/`, `data/cache/interval/`) belong to no repertoire. The manifest format, read by `tools/prep/repertoire.py` and its twin `relay/repertoire.ts`:

| Field | Default | What |
|---|---|---|
| `name` | required | lowercase letters, digits, `-` and `_`; the same as the file name |
| `songsJson` | required | `[{id, title, artist, pool?, cover?, timestamps?: [{time, tag}], ...}]` (`pool`: the song's pool, D178, default "1"), as the playlist-fetcher and `data/repertoires/default/songs.json` write it |
| `audioDir` | required | `<id>.mp3`, or spotDL's `<id> <title> - <artist>.mp3` (`.m4a`, `.opus`, `.ogg`, `.flac` and `.wav` too) |
| `coversDir` | `<cacheDir>/covers` | `<id>.jpg`, served at `/covers/<id>.jpg`; the covers step fetches them from the `cover` URLs |
| `cardsJson` | none | apps/cards' `cards.json`, served at `/cards/cards.json` (its folder at `/cards/`). Without it the Phase uses its placeholder |
| `spotifyFeatures` | `<dataDir>/spotify_features.json` | optional (the Spotify API is deprecated): without the file there is no tempo or key cross-check |
| `dataDir` | `data/out/repertoires/<name>` | `analysis/`, `snippets/`, `report.md`, `keys/`, `stems/`, `signatures/` |
| `cacheDir` | `data/cache/repertoires/<name>` | `<id>/mix.flac`, `<id>/raw.json`, `<id>/snippet.flac`, `<id>/stems/`, `<id>/signatures/`, `keys/`, `stretch/` (gitignored) |
| `overridesDir` | `data/repertoires/<name>/overrides` | the audition page's hand fixes, `<id>.json` |
| `description` | | free text |

Relative paths are relative to the repo root; absolute ones work too.

**Preparing this year's repertoire** once the playlist is final (dry-run on 4 draft songs, 2026-11-25: about 1.5 s to decode, 6 s to analyse and 21 s for stems per song):
1. Fetch each pool's playlist into its own folder (2026: `data/media/2026/pool1/`, `pool2/`): from that folder, `<repo>/tools/prep/playlist-fetcher/venv/bin/python <repo>/tools/prep/playlist-fetcher/fetch.py <playlist id>` writes `output/songs.json`, and spotDL (`main.sh`'s command, with `--output` pointed at the repertoire's one audio folder, `data/media/2026/output/songs/`) downloads `<Spotify id>.opus`. A track listed twice is kept once, with a warning. `./main.sh <playlist URL>` does both into `tools/prep/playlist-fetcher/output/`. It writes `output/songs.json` (with each song's Spotify length and id) and `output/songs/<Spotify id>.opus`: YouTube's own Opus stream, copied, not re-encoded (spotDL's default MP3 output re-encodes it; last year's songs are 128 kbps MP3s). Files named by Spotify id follow their songs when the playlist is reordered, and a rerun downloads only the new songs; a song downloaded by hand goes in as `<Spotify id>.mp3` (or `<id>.mp3`). spotDL works one song at a time with short pauses. **Download with any VPN off:** YouTube answers a VPN's address with "Sign in to confirm you're not a bot" (25 Nov 2026: ProtonVPN was the cause, not the number of downloads). Songs spotDL couldn't get are listed in `output/download-errors.txt`.
2. `data/repertoires/2026.json` (tracked) names the songs list, the audio folder and the cards; `data/repertoires/2026/pools.json` lists each pool's fetched playlist. `tools/prep/.venv/bin/python tools/prep/pools.py --repertoire 2026` writes the songs list, `data/repertoires/2026/songs.json`: every pool's songs with their `pool`, numbered in each playlist's order (D103, U57: pool 1 = 1–70, pool 2 from 71), each order checked letter by letter as the user's sorting tool has it (U58); a song already in an earlier pool is left out of the later one, and everything left out or out of order is printed (`--check` only reports). Each song also gets its print names, the clean title and artist every screen and card shows (Spotify's tags off the title, the main artist only; tools/prep/print_names.py), then the hand fixes in `data/repertoires/2026/print-names.json` (optional, keyed by Spotify id, each with a `note`); `printTitle`/`printArtist` are written only where they differ from Spotify's `title`/`artist`, which stay for fetch and quality, and the analysis and the edition carry the print names as their plain `title`/`artist`. Ids are playlist positions: the audio follows a reordered playlist, but the overrides (hook decisions) and the caches are by id, so a new order means preparing again (move the old `data/out|cache/repertoires/2026` aside first).
3. `npm run prep -- --repertoire 2026`. Run it again after any change: finished work is skipped, and a changed MP3 is decoded and analysed again. The `quality` step flags each source to check by ear (`<dataDir>/quality.json`): under about 128 kbps, a brick-wall low-pass under 15 kHz (a low-bitrate encode upstream; last year's On The Floor and Sense Tu cut at about 10 kHz), more than 5 s off Spotify's length, or version words in the title (Live, Remix, Sped Up, Karaoke…). Options: `--steps decode,analyze,...` (covers, decode, quality, analyze, snippets, validate, keys, stems, signatures, hooks, interval; always run in that order; interval is global), `--song N` (repeatable; validate and keys always cover the repertoire), `--keep-going`. It stops at the first failing step; validate fails on hard errors, and the stems disk guard (10 GB free, 4 GB of stems per repertoire) stops it with exit status 3. On a new repertoire nobody has tagged, the first run analyses every song and proposes hooks (`hooks`), but no song is playable yet, so there are no Check snippets, stems or Signatures.
4. Approve the hooks on the audition page (`/show/audition.html?song=N`, **Automatic hooks**: Best, Main, Reject, nudge), then run `npm run prep -- --repertoire 2026` again: the approved songs become playable and get their snippets, stems and Signatures, and the hooks step proposes again with the stems' vocal entries. **To play before the approval pass (D227):** `tools/prep/.venv/bin/python tools/prep/hooks_auto.py --repertoire 2026 --provisional` approves each song's top candidate as its best hook, marked `provisional: true` in the override (never over a hand tag, a best already approved, or a rejected candidate), then prep again. The flag rides into the analysis: each hook's `provisional` in `<dataDir>/analysis/<id>.json` and `index.json`, and the song flag `provisional_best_hook` in the report. The audition page shows "best (provisional)"; picking a best by hand, nudging it or rejecting it drops the flag.
5. `npm run dev -- --repertoire 2026` (or `npm start -- --repertoire 2026`) serves it. The pages' URLs are the same for every repertoire.

| Page | URL | What |
|---|---|---|
| Show | http://localhost:5174/show/ | Engine and drum in one page. Click **Start show**, then → Next |
| Audition | http://localhost:5174/show/audition.html?song=N | Beat-grid clicks, hook preview, save overrides |
| Tests | http://localhost:5174/show/test.html?run=1 | Offline landing renders, flash-and-click calibration |
| Remote | http://localhost:5174/show/remote/ (or `http://<LAN IP>:5174/show/remote/` on a tablet or phone) | Next, Back, Hold, Hold music, Pace, sound effects, Schedule, cards in play, possible winners |
| Report | http://localhost:5174/data/report.md | Analysis flags and audition queue |

For a projector without the click: `open -na "Google Chrome" --args --user-data-dir=/tmp/quina-show --autoplay-policy=no-user-gesture-required --kiosk "http://localhost:5174/show/?autostart=1"`.

**Show keys:**
- → / Enter: Next (it also releases a Suspense). ←: Back. Space: Hold / release. S: Suspense. M: Hold music. Esc: Panic.
- `+` / `−`: Pace ±1 s. L: lock the Pace. A: auto-advance on or off. 0–4: Phase (auto, early, mid, late, final).
- D: debug HUD. H: hide the controls (projector). `[` `]`: display offset ±5 ms.

**Show URL params:**
- `pace=14`: Pace in seconds.
- `cards=1-200,400-450`: cards in play. Once entered, they are kept in the page's local storage.
- `phase=late`: fixed Phase. `suw=20`: songs until a winner, used only when no cards are in play.
- `auto=0`: auto-advance off. `queue=3,17,45`: a fixed Queue. `autostart=1`. `mute=1`: everything runs but nothing reaches the speakers (headless smoke tests). `fresh=1`: ignore the local journal.
- `fresh=1`: start a new Game instead of resuming the current one. `journal=0`: keep the Game journal in memory only (as `queue=` does).

**Resume after a reload or a crash:** the show page keeps a numbered Game journal (rounds, Queues, landings, undos, the confirmed Line, cards in play, settings) in its storage. A reload resumes the current Game where it was, and the presenters press Next. The journal is in the protocol package (`packages/protocol/journal.ts`, explained in [`docs/protocol.md`](docs/protocol.md#game-journal)), so a cloud store or another device can replay the same journal later.

**Code:** TypeScript everywhere (strict, erasable syntax only, so Node 26 runs the relay and the tests directly), served and built by Vite; Svelte 5 for the remotes' forms (`apps/console/`). The protocol is the linked package `@quina/protocol` (`packages/protocol/`), which imports no engine code, so remotes, the player app and a Worker can share it; [`docs/protocol.md`](docs/protocol.md) explains it. Every tunable number lives in `engine/src/config.ts`.

**Tests:** `npm test` runs the type check (`tsc` on the browser and Node code, `svelte-check`) and the Node tests: planner, solver, Pace, Phase, cards, the show state machine (Back, Hold, cancelled Spins, Pace timing, and a fuzz test that the music never stops by accident), the Check, the tie-free Shuffle on the real cards, the show flow (scene rules, a whole round from Claim to Interval, invalid Claims, Claims during a Spin, the pause, and a fuzz test of every flow command), the Interval playlist (its order, every handover on the one without a gap, a fuzz of them, the real playlist's handover points, the skip and volume through the show, Hold music off), and the journal (replay, `extendJournal` at every split, resuming into each scene). `npm run test:pipeline` (pytest, about 30 s) checks repertoire resolution in Python and in `relay/repertoire.ts`, then prepares a two-song synthetic repertoire in a temp dir (one song without hook tags, no Spotify features), re-runs it to check that nothing changes, and has a relay serve it (and the global Hold music and Interval playlist). `tools/prep/tests/test_interval.py` checks the Interval step's playlist matching, duplicates and slugs, and runs it on three synthetic tracks (one a duplicate).

## What is built

**M0: offline analysis** (`tools/prep/`, Python 3.13 + uv, Beat This! 1.1.0 `final0` on CPU, about 3 s per song)
- Every step works on one repertoire (see Repertoires above), and `prepare.py` runs them in order. The paths below are the default repertoire's; a new repertoire's are under `data/out/repertoires/<name>/`, `data/cache/repertoires/<name>/` and `data/repertoires/<name>/overrides/`.
- `covers.py` fetches missing covers from the songs.json `cover` URLs. `decode.py` decodes each song to `data/cache/<id>/mix.flac` (48 kHz 16-bit FLAC, audio stream only) and records its source in `mix.json`, so a changed MP3 is decoded again.
- `snippets.py` cuts 3 s from each song's best hook (its pickup) to `data/cache/<id>/snippet.flac`, with a loudness trim in `data/out/snippets/index.json`: what a Check plays for each landed song. A few seconds for the whole repertoire, no stems needed.
- `analyze.py` writes `data/out/analysis/<id>.json` (schema v1, B4) and `index.json`. Model output is cached per MP3 sha256 in `data/cache/<id>/raw.json`, so `--derive-only` re-applies hook and override logic in seconds. A file whose content would not change (apart from its `createdAt`) is not rewritten.
- Beat grid: Beat This! beats get a sub-frame refinement (a local linear fit removes its 20 ms frame quantization in steady regions). Downbeats are **regularized** into consistent bars: spurious half-bar downbeats are dropped, missing ones are filled, and real phase changes are followed only when later bars support them.
- Tempo is checked against librosa and Spotify (`data/out/spotify_features.json`). If both put Beat This! at double time, the tempo is halved automatically (song 6, Besos: 209 → 105 BPM). A repertoire without Spotify features (the playlist fetcher doesn't produce them, so this year's has none) is checked against librosa only, and halved only when librosa is at half and Beat This! is at 160 BPM or more (flag `auto_half_time_librosa`, to check by ear; on last year's songs that is Besos alone), and `keys.py` then uses the method that scored best on the default repertoire (`essentia-temperley`), unscored.
- Hooks: the hand tags scatter about ±2 beats around downbeats, and bar RMS can't tell neighbouring bars apart. So snapping is positional and biased toward landing early. A tag within 1.5 beats before a downbeat lands that downbeat, and B starts at the tag rounded up to a half beat (a *pickup*, so the first syllable is never clipped). Any other tag lands the downbeat before it. Mid-bar tags are flagged `snap_ambiguous`.
- **Automatic hooks** (this year's playlist has no hand tags; the user's decision Q33 b): `tools/prep/hooks_auto.py` (the `hooks` step, after the stems) proposes up to five candidates per song in `data/out/hooks/<id>.json`, from three kinds of evidence per bar (`tools/prep/steps/hook_detect.py`):
  - the chorus: the bars are cut into sections by Laplacian segmentation (chroma recurrence and MFCC continuity), grouped into 3, 4, 5 and 6 kinds that each vote, and a section's start scores by its kind's loudness and how often it comes back;
  - an energy jump (the next 4 bars louder than the 4 before), and the singer coming back in (not the first entrance, which is usually the verse).
  - Peaks at least 8 bars apart, each moved by at most a bar onto the song's 4-bar phrase grid when the grid's bar scores nearly as well. On last year's hand-tagged songs the top candidate lands within a bar of a tagged hook in 26 of 77 songs, one of the top three in 48: proposals, not answers.
  - On the audition page (**Automatic hooks**): −4 bars, **Best**, **Main**, **Reject**, **Undo**, and ◀ bar / bar ▶ to nudge an approved one. Approved ones go into the override's `autoHooks` and `analyze.py` adds them after the hand tags (which keep their ids).
  - **The refine step for hand tags:** when the bar next to a tag scores clearly better and sits on the phrase grid, the hooks table's **Suggested** column asks "a bar later?" (or earlier). Yes moves the landing (`hookDownbeats`); No is remembered (`hookShiftDeclined`). The tag itself is always kept. On last year's songs 45 of 386 tags get a suggestion.
- Loudness: integrated LUFS and 4× true peak per song, plus LUFS over 8 s from each hook. The engine trims each landing to −14 LUFS (hook-based).
- A song without hook tags gets no hooks and the flag `no_hook_tags`, so the engine leaves it out (`playableSongs` needs a valid hook). It is not a hard error.
- `validate.py` writes `data/out/report.md`: the playable count, the songs without hook tags, whether Spotify features exist, the flags, an audition queue ordered by severity, and per-song levels.
- `data/repertoires/default/overrides/<id>.json` holds hand fixes, merged last: `downbeatShiftBeats`, `tempoFactor`, `beatsPerBar`, `hookDownbeats`, `hookPickupBeats`, `hookNudgesSec`, `disableHooks`, `hookTimes`, `exclude`, `note`. The audition page writes these through the relay and re-derives on Save.

**M1: show engine** (`engine/src/`, TypeScript)
- `plan/planner.ts` is a pure function, tested in Node, with two shapes. **S1, "ride A, then land":** T is one of A's downbeats and A's exit move ends there. **S2, "exit, bridge, land":** A exits on its downbeat e, and a build of N bars *on B's grid* fills [e, T], so B's riser, snare roll and low-passed Tease are phase-locked to its hook without time-stretching. The Spin window comes from the Pace. **B lands on A's phrases:** counted from the hook where A landed, the landing goes on a 4- or 8-bar boundary of A. An S2 bridge takes the place of A's last bars, so the landing keeps A's 8-bar phrase; when B's bars are too far from A's to reach that, A completes its phrase and the build follows. The search tries the Pace's window, then anything up to the Spin's 11 s limit (a presenter's Next waits for a phrase), and only then a plain bar. Inside a pass, candidates are costed by distance from the target Spin length plus phrase class (8-bar = 0, 4-bar = 1, bar = 2.5).
- **Every transition is a DJ move with effects, never a bare fade, and the intensity grows with the Phase** (the user's first listen: too intense everywhere). Early moves are light, quick and clean: a cut on the one (often after a filter sweep), a short echo, a drum or stem swap, the Blend when it fits; most early landings have no impact and no riser. Each Phase's `dress` (config.ts) sets the riser's chance and level on S1 and S3 moves (an S2 build keeps its riser) and the Spin's whoosh. The hit is drawn apart from the landing layer: none, the sub drop alone, or with samples (`MOVES.landing.impactKinds`: none on 65% of early landings, never in final). The orchestra hit only comes late and in final, never within 6 (late) or 3 (final) transitions of the last one. The recipes:

  | Recipe | What you hear |
  |---|---|
  | R1 Slam cut | A's high-pass and a riser climb over its last bar, a swell, then a hard cut on the one |
  | R2 Echo-out | Tempo-synced echo (½ or ¾ beat, feedback 0.5) while A's high-pass and the echo return sweep up, a riser, then the hook |
  | R4 Loop roll | A's bar stutters in shrinking slices (1 → ½ → ¼ → ⅛ → 1/16 beat) with the filter opening, a riser, then the landing |
  | R5 Brake / spinback | Tape-stop (rate → 0, low-pass closing, falling noise) or a reversed rewind of A, a breath of silence, then the hook |
  | R6 Reverb wash | A dissolves into a big high-passed reverb, and the hook comes out of the cloud |
  | R7 Build & land | A exits (echo, roll, brake, spinback or wash, rotated), then 1–4 bars of noise riser plus a snare roll accelerating ¼ → ⅛ → 1/16 → 1/32 with rising pitch, a Tease of B through a closed low-pass, the music-bus high-pass sweeping up, a beat of silence, and the landing |
  | R8 Blend | B's own groove, stretched to A's tempo by Rubber Band R3 and locked to A's downbeats, comes in under A for 2–8 bars: drums first, then (tempos within ±4% and compatible keys) B's bass while A's bass is cut. A echoes or washes out under a riser and swell, and B lands on its hook at its own tempo with an impact. Only for the 37% of pairs within ±8% tempo |
  | R10 Power-down | Final phase: 1.5 s tape-stop, a heartbeat on B's beats, the build, half a bar of silence, and the biggest layered impact |
  | D1 Trans gate | A chopped on its own grid by a gate ladder that speeds up to 1/32 (partial early, silent late), or pumped like a sidechain with kicks; its high-pass climbs under a riser |
  | D2 Stop-time hits | A only on chosen beats with silence between ("pam · pam · pam ·") for the crowd to shout, the last hit ringing, a gap of at least a beat, a bigger impact; at most one in six |
  | D3 Spiral echo-out | A's last beats caught in an echo whose delay shrinks, so the repeats climb in pitch into a swirl, cut dead before the hook |
  | D8 Stem peel | A's drums, bass and the rest removed one by one (stem lanes) until its singer is left, the voice thrown into the echo, then the full hook |
  | D10 Drum swap | A's drums replaced on a downbeat by B's stretched drums under A's voice (sometimes juggled), the bass swapped in the last bar when keys and tempos allow |
  | D11 Vocal-chop build | R7's build with B's first syllable chopped faster and higher on B's grid ("ca-ca-ca-CARAMEL"), then the full word on the pickup |
  | D6 Fake drop | Late and final, on a long bridge: a build peaks into a beat of silence where the hook should be, then a bar of something else (B's drums alone, a comedy sample, or heartbeat kicks), a faster re-build, and the real landing, bigger; about once a climb |
  | D7 Pitch-up rush | A becomes the riser: its tape speeds up 2–5 semitones over its last bar, high-pass opening, then a breath and the hook; late, a gate sometimes chops it on its rising beats |
  | D15 Instrumental braker | A's band grinds to a halt while its singer carries on dry and at speed (stem lanes braking with the band); the voice is thrown into the echo, then B lands |
  | D16 Acapella-in mashup | For pairs within ±4% with agreeing keys: A's singer drops out on a downbeat and B's voice, stretched to A's tempo, sings over A's band for a bar or two, then B's own chorus lands |
  | D19 Scratch-in | R7's build with B's first syllable scratched on B's eighths (baby, chirp or forward strokes), released forward into the pickup |
  | D20 Count-in | A muffles over its last bar (its low-pass closing) while claps or stomps count the beats in, louder at the end, then a clean cut on the one: light, and the room can clap along |

  The landing layer rotates (reverse cymbal, a dry landing, D12's pre-verb swell of B's own first beat or first word, D14's tape start: B powering up from a growl to full speed exactly on its pickup, or the open landing: B's low-pass opening onto its downbeat), R7's bridge pattern is drawn apart from its exit (roll, half-time, kick roll, clap-along; the gate and the spiral are exits too) and may carry D5's riff bed (B's riff looping under the build), R1, R2, R4 and R5 have variants, D9's Ghost Tease (B's voice only through the reverb, sometimes turning into its dry voice) decorates S1 moves and S2 bridges, and an S1 gap of a beat or more may hold a one-beat chop or scratch of B's first syllable. Details, Phase weights and what is not built: [docs/dj-techniques.md › Built](docs/dj-techniques.md#built).

- **Phases escalate the spectacle; they don't add or remove it.** Early: short 1–2 bar builds and quick moves. Mid: 2-bar builds, a ½-beat gap, and sometimes a Tease. Late: 2–4 bar builds with the low-pass Tease and a 1-beat gap, snare up to +7 semitones. Final: R10 power-down, D2's crawl, a long D8, the fake drop, the braker, the final gate or spiral. Rotation: the previous recipe is penalised, the same family is never used three times in a row, two theatrical moves never run back to back, and the build's exit move rotates.
- **Stem Teases.**
  - `tools/prep/stems.py` runs Demucs `htdemucs` on MPS, about 20 s per song. It writes drums, bass and vocals at half scale (no clipping), in windows around the hooks and the intro (`data/cache/<id>/stems/`, with metadata in `data/out/stems/<id>.json`), sample-aligned with `mix.flac`.
  - When the next song has stems around the chosen hook, and they are audible in the bars before it, the build Teases with **B's own drums, then its bass for the last bar**, at B's tempo and phase-locked to the hook. The full song bursts in on the pickup.
  - Without stems, the low-passed Tease remains. All 77 songs have stems.
- **Blend preparation.**
  - The next song's hook is chosen as soon as that song is decoded. When the pair's tempos are within ±8%, the relay renders B's 8 bars before that hook at A's tempo (`tools/prep/stretch.py`, Rubber Band R3, with stems, about 1–2 s, cached).
  - Keys come from `data/out/keys/` (essentia, Temperley profile; `tools/prep/keys.py`); B's bass layers only if the keys are compatible with a confidence of at least 0.7.
  - If no landing fits the blend, the planner falls back through other real moves (R7, R2, R1), never the bare fade.
- **Vocals across a transition** (`VOCALS` in config.ts, from the stems' bar levels):
  - **A sudden vocal entry** (B's singer silent in the two bars before its hook and singing on the downbeat) gets a fast, clean move straight into the voice: a cut on the one, a short echo or a strip-down are favoured (builds rare), the silence before it is none or half a beat, and B's Signature is teased before it more often. Last year's songs: 4% of transitions.
  - **Call and response** (B sings at its hook and A sings where it may leave): a landing right after a sung bar of A is preferred within each search pass, so A's line is answered by B's on the downbeat, and the moves that keep A's voice to the end are mildly favoured.
- **Signatures** (GLOSSARY): short, recognizable **instrumental** pieces of a song, teased just before it lands. Never a vocal line (the user's first listen), and never after the landing.
  - `tools/prep/signatures.py` proposes candidates from the stems' bar levels (`tools/prep/steps/signatures.py`) and cuts each without the vocals to its own file (`data/cache/<id>/signatures/`, with metadata in `data/out/signatures/<id>.json`). There are three kinds, two bars each, starting on a downbeat:
    - a **riff** is the steadiest, loudest two bars of the instrumental intro, before the first sung bar;
    - a **build** is the two bars leading into a chorus (a valid best or main hook), scored higher when nothing is sung over them and the chorus hits harder after them;
    - a **motif** is the chorus's instrumental line (the "other" stem over the hook's first two bars), when it holds its own against the singer.
  - **The automatic pick:** per song the best candidate scoring at least 0.6 plays (`AUTO_MIN_SCORE`). On the audition page: Play, In song, **Pick** (this one plays instead), **Veto** (never this one; the next best is picked), **Undo**, and **No Signatures for this song**. Decisions go into `data/repertoires/default/overrides/<id>.json` (`signatures`, `signaturesOff`). On last year's songs, 38 of 77 get an automatic pick (29 riffs, 6 motifs, 3 builds).
  - **Placement:** at most one per transition, B's only, with a chance that grows with the Phase. Its last bar ends on the landing (a build is B's own way into its chorus), and it is faded out at B's pickup. On B's own grid over an S2 bridge or an opener build, from the bridge's start; over A (S1, S3) only on A's own downbeats with agreeing keys and tempos within 4%. Its head may be cut when it cannot start yet, as long as half of it plays. A build never doubles B's own Tease.
- `audio/`: `AudioBufferSourceNode.start(T − lead, hook − lead)`, sample-timed. Decks run trim → HPF → LPF → fader with a post-fader echo send, into a master limiter. Songs come from FLAC (the same PCM as the analysis) with a sliding decode window (previous, current, next, next+1).
- `wheel/`: shuffle-test's `physics.js` is copied with its logic **unchanged**, only typed (`shuffle-physics.ts`). `solver.ts` draws a random spin, steers its drag toward the wanted duration, bisects the top speed until it rests on the target card, and time-scales the replay (0.85–1.2×) so it locks at exactly D. It always travels more than a lap (except Back). The drum is drawn from `AudioContext.getOutputTimestamp()`, and its ticks are scheduled on the audio clock.
- **Suspense** (`plan/suspense.ts`, GLOSSARY): the presenters hold the next transition open, and it is never started automatically.
  - **A keeps playing** and repeats the 4-bar phrase it is in (`plan/loop.ts`, counted from the hook it landed on): each repeat is re-cued a moment ahead on its own downbeat. The build grows over it bar by bar on A's downbeats: a riser, a snare roll and heartbeat kicks, more intense over about 24 s, while A thins out (its high-pass climbs to 350 Hz, it dips 3 dB). Every bar is self-contained and scheduled 0.35 s ahead.
  - **The drum hovers over three pending songs**, the real next one among them in a seeded order. From the second bar of each pass a Decoy tease of one of them plays over A, in turn: its hook, low-passed at 1.1 kHz, cut by a tape stop before the phrase's last bar, as the drum swings to its card and sways there. A tease never counts.
  - Next, or a second Suspense press, releases it: B lands at the end of the first pass that leaves room, on A's phrase boundary, after A's exit move (echo, wash, brake or spinback) and the final bar's build and silence. It releases by itself after 30 s. The drum brakes onto the target exactly at the landing.
  - Back or Hold cancel it like a Spin; A plays on from the phrase it is in.
  - Without phrases to count (nothing playing, or no landed hook), A exits as it opens and the build loops on B's grid instead.
- **The show state machine** (`show/show.ts`) is pure: no Web Audio, no DOM. It takes commands, clock ticks and decode results, and returns effects that `main.ts` carries out on the audio graph, the drum and the network. States are `locked`, `idle`, `playing`, `transition` and `hold`.
  - **Pace:** auto-advance keeps landing to landing near each song's slot: the Pace (14 s by default; presets 11–30 s, ±1 s) for a song already played in an earlier round, and the Pace × 22/14 (22 s) for a song's first play in the Game, which also lands on its best hook (D174, D175). The Spin takes about half the slot (3–11 s), and the landed song keeps playing under it. Late phases stretch the slot by 25%, and a landing that probably completes a card stretches it by 50% (a minimum, so a Claim has time). In the final phase, auto-advance is off unless the presenters keep it on.
  - **On the phrase:** the automatic Next lands on the playing song's 8-bar boundary nearest its slot, between ×0.75 and ×1.4 of it, else a 4-bar one (an 8-bar boundary wins unless the 4-bar one is nearer by 15% of the slot). It presses one Spin before that boundary (at most 10 s, so a bridge on a slower B stays under 11 s). A slow song whose phrases straddle the range takes the nearest boundary in ×0.6–1.6. A gap is then a whole number of phrases, and the Drift nudge evens the round out. After a Hold, the same applies around the usual breather.
  - **Schedule and Drift:** the round's and the game's end are estimated from the Queue position, the expected Line and Bingo songs, Check times and intervals. In early and mid, the Pace is nudged by up to ±20% to recover Drift, unless it is locked.
  - **Hold:** the songs duck by 14 dB under the presenters' voices. After 40 s, or when the song runs out, Hold music takes over (U205 asks whether Parlem should loop the ducked song instead). **A song left playing never hands over to other music by itself (D239):** in Aguanta, or with auto-advance off and nobody pressing Next, near its end its last phrase (8 bars, else 4, before the outro) repeats, else its last 4 bars, until Next or a Hold; only a song with no beat grid still runs out into Hold music. Releasing un-ducks the song, or, on Hold music, builds into the next song. Hold during a Spin cancels it.
  - **Hold music:**
    - The user's tracks go in `data/media/hold/` (gitignored). `tools/prep/hold.py` decodes each one to `data/cache/hold/` and picks seamless whole-bar loops into `data/out/hold/<name>.json`, which the engine plays with native `loopStart`/`loopEnd`.
    - It finds the composer's loop body by self-similarity, sample-exact (both Mario Kart tracks), and keeps bar loops as fallbacks. A body loop plays the track's intro once, then loops the body, like the game; it never restarts from the top.
    - Folders set the mood. Everything in `hold/` is fail music: it plays after Back, and later after a failed Check. `celebration/` is victory music.
    - Tracks of a mood take turns. A synthesized chiptune placeholder covers ordinary Holds until there's a track for them.
  - **Interval playlist** (`data/media/interval/`, spotDL's `NN Title - Artist.mp3` plus `playlist.spotdl`, gitignored):
    - `tools/prep/voices.py` (the prepare step `voices`, global): the automatic voice cues (D198, D202–D204). Each of the protocol's `VOICE_CUES`, the `chime` and the round's `fanfare` comes from the user's recording in `data/media/voice/<name>.<mp3|m4a|wav|flac|ogg|opus>` (gitignored, synced to R2), else from a placeholder (macOS `say`, tones), decoded to `data/cache/voice/<name>.flac` at one loudness; `data/out/voice/index.json` lists them with `placeholder: true` for what's still to record. The relay serves `/voiceaudio/<name>.flac` and `/data/voice/`.
    - `tools/prep/interval.py` (the prepare step `interval`, global) takes title and artist from `playlist.spotdl`, plays a recording once (#04 and #16 are the same "New Look"), decodes each track to `data/cache/interval/<slug>.flac` and writes `data/out/interval/<slug>.json`: the Beat This! grid with analyze.py's refinement and regularized downbeats, the loudness trim to −14 LUFS, and where the sound starts and ends and its closing fade starts. `data/out/interval/index.json` lists the tracks, the duplicates and the entries without a file.
    - `engine/src/interval/plan.ts` is the pure plan: the Game's shuffled order (no repeat until all have played, kept across a reload) and every handover. `audio/interval.ts` (`IntervalPlayer`) carries it out on its own bus under the music.
    - The transitions are modest, with no drum: the outgoing track echoes out on its downbeat 8–12 s before its end, and the next track's downbeat lands on that one, after two bars rising under it (a swell or a filter opening) when the tempos are within 4%, or after only its pickup with its filter opening on, when they aren't.
    - A round flows into it without silence: the victory track (or Hold music, or the Winning song's loop) plays on until the first track is ready, then hands over on its own downbeat. It plays under the round intro and the Shuffle, and the first Spin builds out of it. The console can skip a track (`intervalSkip`, on the next downbeat) and set its volume (`setGame {intervalVolumeDb}`); the state shows the track (`intervalMusic`).
  - **Hold music off** (`setGame {holdMusicOn: false}`): a Hold keeps the song ducked instead of switching to Hold music after 40 s; Hold music still covers silence.
  - **Stingers** (`data/media/stingers/`) are on the tablet's sound pad. "Final lap" plays automatically once per climb, as the Phase first turns late; `config.ts` `ENGINE.finalLapStingerPhase` sets which phase triggers it.
  - **Back** undoes the last landing: the song rewinds out (a spinback), stops counting and becomes next again. The drum turns back one card onto the previous song, and Hold music starts. It is repeatable, and the Queue's order never changes. Back during a Spin cancels it: the drum brakes back onto the current card, and the outgoing song stays (restored) if its exit move hadn't started; otherwise Hold music covers. Within 0.15 s of the landing it acts right after the landing instead.
  - **Phase:** from the cards in play valid for the round (normal cards, or special ones in the special round) and the known Queue, blurred by `game/phase.ts`: late starts 3–8 songs before the expected win, with occasional false alarms, and final covers the last 1–3 songs. It resets towards the Bingo when a Line is confirmed. Without cards in play it falls back to a "songs until a winner" placeholder.
  - **Possible winners:** after each landing, the tablet privately lists the cards that now have a Line or a Bingo.
  - **Panic** fades everything out in 0.3 s. A runtime watchdog starts Hold music whenever the state says music should be playing and nothing is.
  - **The show flow** (`show/flow.ts` and the scene rules in [`docs/protocol.md`](docs/protocol.md#scenes)): scenes from `before` to `after`; the public **tie-free Shuffle** (`game/shuffle.ts`: deterministic reshuffles of a secret seed until neither the first Line nor the first Bingo is a Tie among the cards in play; 8 s of animation before anything lands); **Claims** and their **Check** (`game/check.ts`: the completed row or all 12 songs, 2.5 s hook snippets for ✓ and a synthesized "broken record" for ✗, timed in advance, everything else ducked far down); the presenters' verdict (the Failure fanfare and the error Hold music, or the **Celebration**: the Clear fanfare, then the Winning song's hook looped in whole bars, or the victory track); the **Interval** (by hand, or 60 s after a Bingo's Celebration) and its playlist; **Winners** with private names and notes; the technical **pause**. All of it is journaled, so a resumed laptop comes back in the same scene. Every number is in `config.ts` `FLOW`.

**Relay and remote:** `relay/server.ts` serves the pages (Vite in development, `dist/` with `--dist`) and the audio, and runs a WebSocket hub on `/ws`. `--repertoire` picks the repertoire whose files the song routes serve (`/audio`, `/stems`, `/signatures`, `/snippets`, `/stretch`, `/analysis`, `/data`, `/covers`, `/cards`, `/api/override`); `/holdaudio`, `/data/hold`, `/intervalaudio` and `/data/interval` are the same for every repertoire. The URLs never change, so the repertoire's media is revalidated by ETag instead of cached for a day. It forwards commands to the show page and the show page's events to everyone else, and caches the last state for new clients. `remote/` is the tablet and phone remote: Next, Back, Hold, Hold music, Pace presets, ±1 s and lock, auto-advance, the Schedule and Drift, a sound-effects pad, cards in play, possible winners, the Phase override, Line confirmed, New round and Panic (these two need a second tap).
