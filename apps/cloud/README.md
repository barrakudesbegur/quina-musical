# Cloud: the Game's home in Cloudflare

The cloud backend of the Quina Musical ([ADR 0003](../../docs/adr/0003-cloud-owns-the-game-laptop-owns-playback.md)): a Cloudflare Worker and **one GameRoom Durable Object per edition**, with SQLite storage and the WebSocket Hibernation API. The show laptop owns playback and keeps journalling offline. The cloud owns the Game: it takes the laptop's journal, feeds the players' phones, and exports everything as JSON.

```
show page ──(relay /ws)── laptop link ──(wss /ws/show, Access service token)──┐
                          laptop/        journal copy on disk                 │
                                                                              ▼
phones ──(wss /feed?cards=…, public, receive only)──────────────▶ Worker ─▶ GameRoom (SQLite: journal + 1 snapshot row)
consoles ─(wss /ws/console, the relay protocol, Access)──────────▶   │      commands → link → relay → show
admins ──(https /api/export, /api/stats, Access with Google)─────▶   │
player app, covers ── static assets, never through the Worker (free) ┘
```

Terms follow [GLOSSARY.md](../../GLOSSARY.md). The shared contracts are in `@quina/protocol` (`packages/protocol/`): the commands, the events, and the Game journal with `replayJournal`/`extendJournal`. The public feed for phones is [`packages/protocol/public.ts`](../../packages/protocol/public.ts).

## Run it

```sh
npm install                          # at the repo root (npm workspaces)
cd apps/cloud
cp .dev.vars.example .dev.vars      # the dev Access bypass (localhost only)
npm run dev                          # wrangler dev on http://localhost:8787 (static files: static/ only)
npm run assets                       # dist/: static/ + the UI build + cards.json + covers as JXL + JPEG (sips, cjxl)
npm run link                         # the laptop link: relay ws://localhost:5174/ws → ws://localhost:8787/ws/show
npm run media -- push                # the repertoire's prepared media → the cloud's private R2 (pull on a takeover laptop)
npm run media -- prune               # the bucket's repertoires, real size (10 GB free) and unnamed blobs; --yes deletes those; --repertoire NAME drops one first
npm run preflight                    # before every rehearsal and show: a pass/warn/fail table (exits 1 on any FAIL); --laptop-only without the tablet
npm test                             # typecheck, Node tests, workerd tests (about 10 s)
npm run loadtest -- --report reports/loadtest-$(date +%F).md   # 400 phones (about 1 min)
```

A phone in a browser console: `new WebSocket('ws://localhost:8787/feed?cards=12,123').onmessage = (e) => console.log(JSON.parse(e.data))`.

## Routes

| Route | Who | What |
|---|---|---|
| `GET /feed?cards=12,123` (WebSocket) | anyone (phones) | The public feed: a `public.state` snapshot, then `public.delta` messages. Phones send nothing. The card numbers (at most 30) feed Admin's anonymous "cards opened on phones" |
| `GET /ws/show` (WebSocket) | the laptop's Access service token | The laptop link: journal uploads, live events, a keepalive; the consoles' commands back ([`src/link-protocol.ts`](src/link-protocol.ts)) |
| `GET /ws/console` (WebSocket) | organizers (Access) | A console through the cloud, speaking the **relay protocol**: `hello` as `tablet` or `admin`, then commands. It gets the show's events raw (private ones included, as on the relay; never the journal) and a `relay.clients` list that merges the laptop's relay with the cloud's consoles. With the laptop offline, a command is refused at once as `notReady` |
| `GET`, `PUT /api/plan` | admins (Access), and the laptop's service token (the edition tool, D116) | The edition's Game plan (`GamePlan`, protocol/plan.ts). PUT saves it whole, checked with `checkGamePlan` and only for this edition (400 with every error otherwise). Phones get only what they may see of it in the feed (`publicPlan`: the revealed rounds' prizes, nothing of a locked round, no cheat sheet; rounds reveal with the journal's `prizes.revealed`), consoles get it whole as `relay.plan`, and the laptop link keeps a copy in `data/link/cloud-plan.json` (`{ savedAtMs, plan }`), which the relay pushes to the laptop's screens. A plan saved on the laptop with no cloud (the relay's `PUT /api/plan`) comes up as `link.plan` once the cloud is back: the newest save wins. The plan's `volumes` (the sliders a fresh Game starts with, D139) are the tablet's: the cloud folds the journal's newest slider moves into them ([`volumes.ts`](src/domain/volumes.ts)), and a plan saved from Admin or the laptop keeps the cloud's, so a stale copy can't undo a move. The link also copies the plan's images (`/media/…`, with their JPEG XL) into `data/link/media/`, which the relay serves |
| `POST /api/media` | admins (Access), and the laptop's service token (the edition tool's logos) | Upload a sponsor logo or prize picture: the PNG or JPEG fallback (at most 300 KB; the body is the file; `?name=` optional). Answers `{ path: '/media/<key>.png', key }`, which goes in the plan; the key is its content hash, and the same file twice is stored once. WebP and SVG are refused |
| `PUT /api/media/<key>.jxl` | admins (Access), and the laptop's service token | Attach that image's JPEG XL (Admin encodes it in the browser; at most 300 KB) |
| `GET /api/media` | admins (Access), and the laptop's service token | Every uploaded pair, newest first, for Admin's picker: `{ media: [{ key, name, fallback, jxl, contentType, size, jxlSize, uploadedAtMs }] }` |
| `GET /media/<key>.<ext>` | anyone | An uploaded image, immutable (cached a year by browsers, and by Cloudflare's cache on a custom domain). `.jxl` answers with the fallback's bytes (cached 5 minutes) until the JPEG XL is uploaded, so `<picture><source type="image/jxl" srcset=".jxl"><img src=".png"></picture>` never breaks |
| `GET /api/games` | admins (Access) | The edition's Games, newest first (rehearsals, the night): last entry, rounds, which is current, and for the current one its resume point (round, kind, Shuffle seed, position, Line), to prefill a manual `resumeAt`. The seed is secret. `flaggedDecisions`: accepted claims to look at, each with its `reasons`: `notPassing` (the card didn't pass: a win by hand from a Review, D121, says `manual`) or `notSold` (not among the cards in play). The cloud never refuses an entry for a game rule (D65), it flags. |
| `POST /api/resume` `{ gameId }` | admins (Access) | Admin's manual resume: that Game becomes current and its whole journal goes to the laptop, which writes `data/link/resume.json` for the show page's boot check |
| `GET /api/phones` | admins (Access) | Phones following the feed now, and which card numbers (anonymous): "cards opened on phones" |
| `PUT`, `GET /api/notice` `{ notice }` | admins (Access) | The banner on every phone (at most 200 characters; null clears it). GET reads it back as the phones have it, so Admin's form starts from it |
| `PUT`, `GET /api/sounds` `{ soundsDefault }` | admins (Access) | The player app's default for interface sounds; a player's own choice wins. GET reads it back |
| `GET /api/sync` | the laptop's service token | The private R2 bucket at a glance (`npm run media -- prune`): `{ repertoires: [{ name, files, bytes, blobs, updatedAtMs }], blobs: { count, bytes }, unnamed: { count, bytes }, totalBytes, freeTierBytes }`. `totalBytes` is the bucket's real size, each blob once; `unnamed` is what a prune would delete. 503 until the bucket exists |
| `GET /api/sync/blobs[?cursor=]` | the laptop's service token | One page of the bucket's blobs (at most 1,000, one R2 list call): `{ blobs: [{ sha256, size }], cursor }`, `cursor` null on the last page |
| `PUT`, `GET /api/sync/blobs/<sha256>` | the laptop's service token | One file's content, stored once by its SHA-256 (64 lowercase hex) under `blobs/<sha256>`, immutable: R2 refuses a body whose hash isn't the key's (400). PUT needs a `content-length` up to 100 MB (the Free plan's request limit); GET answers the bytes, `no-store` |
| `PUT`, `GET`, `DELETE /api/sync/manifests/<repertoire>` | the laptop's service token | A repertoire's manifest, `manifests/<name>.json`: `{ v: 3, repertoire, files: { "<root>/<path>": { size, sha256 } }, updatedAtMs }` (at most 4 MB). PUT checks its format (400) and that every blob it names is in the bucket (409 with the first missing hashes); GET is 404 for a repertoire with none. DELETE (with `x-confirm-repertoire: <name>`) drops the manifest only; its blobs go with the next prune |
| `POST /api/sync/prune` `{ sha256: [...] }` | the laptop's service token | Delete 1 to 1,000 blobs (one R2 call), only if no manifest names any of them now (409 otherwise): what `npm run media -- prune --yes` sends |
| `GET /api/export` | admins (Access) | Every Game of the edition: journal entries, each Game replayed with the protocol's reducer, and the public state |
| `GET /api/stats` | admins (Access) | Connections, messages and SQLite rows since the GameRoom last woke |
| `GET /api/ping` | signed in (the laptop's token, or organizers) | The cloud's clock, edition and current Game: the preflight's sign-in and clock check |
| `GET /api/health` | anyone | `{ ok, edition }`, without waking the GameRoom |
| anything else | anyone | Static files from `dist/` (`npm run assets`): the player app at the root (it takes every page, such as `/26/123`), `console/`, `admin/`, `assets/`, `cards/cards.json` with `cards/card-types.json` (each printed type's name, colour, title and price), `covers/<id>.jxl` with `covers/<id>.jpg` as the fallback, the player's PWA (D221, D222: `player-sw.js`, `player.webmanifest`, `icons/`, never kept by phones; hashed `assets/` kept a year), and `sw.js`, which removes last year's service worker. Served without running the Worker, with `static/_headers` |

## How it works

- **The journal is idempotent by `seq`** ([`src/domain/ingest.ts`](src/domain/ingest.ts)). The GameRoom extends its one snapshot row with `extendJournal`, so it never reads history back. A resent entry is skipped, a gap gets `cloud.need` (never applied out of order), and a *different* entry with a known `seq` is a `cloud.conflict` (uploads stop and a person decides). Entries are checked field by field before replay ([`journal-check.ts`](src/domain/journal-check.ts)).
- **Games inside an edition.** One GameRoom per edition (`EDITION = "26"`, the year tag in the players' links), with a current-Game pointer. A rehearsal or a `?fresh=1` show is another Game: its own journal, and the phones' rounds reset (their saved cards don't). Going back to an older Game rebuilds it from its stored entries.
- **The public feed is a whitelist** ([`src/domain/projection.ts`](src/domain/projection.ts)). An exhaustive switch over journal kinds plus named live events. It never carries the Queue, the next song, possible winners, the Phase, the real Heat, `roundEndMs`, a Check's reveals or outcome (phones get only which card is checked, then the verdict), a Review, claim details, the volumes, the Desgraciat's finalists (U150), or winners' names. Pausa goes public only with its overlay (D135). A song reaches phones only once its landing is journalled. A late upload (after an offline stretch) never stops a newer Spin. The drum's seeds are public (D237), so a phone's drum matches the projector's: `PublicRound.drumSeed` and `PublicSpin.spinSeed`; and the Spin carries its landing song, `PublicSpin.targetId`, from its start (D277, U206), which phones reveal only at `landAtMs`; never `drum`'s other fields (`removeId`, `minLaps`). One reducer, `applyPublic`, runs in the GameRoom and on every phone; `seq` gaps make a phone resync.
- **The laptop link** ([`laptop/`](laptop)) is a Node process next to the relay, not the show page. It can send the Access service token headers, keep the journal on disk, and later download R2 media, and a cloud problem can't touch playback. It uploads one batch at a time (up to 200 entries), resends unanswered ones, reconnects with full jitter (1 s doubling to 30 s), and sends a keepalive every 20 s when idle. A newer laptop replaces it (close 4001) and it doesn't fight back.
- **Consoles through the cloud** ([`src/domain/consoles.ts`](src/domain/consoles.ts)). The cloud checks a console's command with `checkCommand` and hands it to the link, which gives it to the relay; the show checks it again. While at least one console listens through the cloud, the link forwards every event except the journal and engine health (`state` at most 4 a second); otherwise only what phones need, to save requests. The relay's client list lives in the laptop socket's attachment, so it survives hibernation. A console that has just connected sends `getState`. For D234's two-level-button lock each command carries the console's own `from: 'cloud:<its hello clientId>'` (none when that isn't a plain id; a `from` the browser set is dropped), and the link hears which consoles are connected (`cloud.consoles`, with their `ids`, from the live sockets) and hands that list to the relay, again whenever its relay socket reconnects and empty when the cloud drops, so the engine lets go of a button a cloud console held when it leaves.
- **Taking over and resuming.** The welcome names the cloud's current Game. A link whose copy is behind (a new laptop, or entries another laptop wrote) fetches the rest (`link.fetch` → `cloud.journal` chunks) into its disk copy, never over another Game. Admin's `POST /api/resume` pushes a whole Game the same way, plus `resume.json`. The relay serves the link's folder read-only at `/cloud/` (patch 0003), so the show page's boot check and the LAN screens can read the journal copy, `resume.json` and `plan.json`. Offline, the engine's `resumeAt` rebuilds a round from its Shuffle seed (journalled as `round.resumed`, which the projection shows as the round whole).
- **Media sync** (`npm run media -- push|pull|prune`, [`laptop/media-sync.ts`](laptop/media-sync.ts), [`src/domain/media-sync.ts`](src/domain/media-sync.ts)).
  - What: the repertoire's prepared playback files (decoded songs, stems, Signatures, analysis, overrides, covers, the Hold and Interval music, voices, effects, stingers, cards), never the Blend renders or the Spotify features. 2026's repertoire is 2,796 files, 8.2 GB.
  - The bucket is content-addressed (D248): each distinct file once, as `blobs/<sha256>`, and one manifest per repertoire, `manifests/<name>.json`, mapping each readable sync path (`<root>/<path>`) to its size and hash. The shared music (Hold, Interval, voices, fx, stingers) and a track both pools hold under two song ids are stored once; dedup comes from the hashes, never from song ids (they are per repertoire). Laptops keep their readable folders and names exactly as the relay serves them; only the bucket stores by hash.
  - Push: hashes every file (cached by size and mtime in `data/link/media-index.json`: 7.5 s for 6 GB), lists the bucket's blobs (one request per 1,000), uploads only the hashes it lacks (two paths with the same content go up once), then PUTs the manifest last; the Worker refuses a manifest that names a missing blob, so a pull never meets one. A push that stops leaves the last whole manifest in place; run again, it lists the bucket and sends only what is still missing. Nothing changed: nothing goes up and the manifest stays. `--dry-run` says what would go up, by root.
  - Pull: reads the manifest and writes each path missing or different here into its readable place: the blob goes to `<file>.part`, its size and hash are checked, then it's renamed. A blob several paths share is downloaded once and copied (a copy-on-write clone on APFS); one an unchanged file here already holds is copied from it. It never deletes anything, and run again it resumes. It works into an empty data folder: what a spare laptop does before the night, after which it runs offline (the show never reads R2). `--into <dir>` pulls into another folder instead, each folder at its place under it as under the repo: a check that the bucket alone rebuilds the repertoire.
  - Prune: `npm run media -- prune` shows each repertoire, the bucket's real size and the blobs no manifest names (a replaced voice or hook), with their count and size; `--yes` deletes them. `--repertoire <name>` first drops that repertoire's manifest (with `--yes`), so the blobs only it named go too. The Worker deletes a blob only while no manifest names it. Nothing ever expires by date (D246).
  - Each request (a blob's upload or download, a page of the list, a manifest, a prune) is tried up to 5 times on a failure that may pass (a network error such as an HTTP/2 stream reset, HTTP 5xx or 429, a download cut off), with full jitter (1 s doubling, capped at 30 s); 401, 403 and other 4xx stop at once, and so does a file that changed since the scan.
  - Requests: a push is 1 (manifest) + 1 per 1,000 blobs (list) + 1 per blob uploaded + 1 (manifest PUT); a pull is 1 + 1 per distinct blob downloaded. For 2026 that's about 2,800 each the first time, a handful after a change. No request comes near the Worker's ~1,000 R2 operations: the manifest PUT and `GET /api/sync` make one list call per 1,000 blobs (3 for 2026) plus one call per manifest.
  - When: the day before the show at the latest, and again after any change (only the new hashes go).
- **Preflight** (`npm run preflight`, [`laptop/preflight/`](laptop/preflight)), run before every rehearsal and show. FAIL means it would hurt the show; WARN is worth a look; the exit code is 1 on any FAIL.
  - Repertoire: songs analysed with their audio; every card's type in card-types.json, with each side its type prints (D178), every song on a side playable and in that side's pool; WARN while songs land on a provisional hook (D227); every voice cue with its prepared file (FAIL if not; WARN while any is a placeholder); fanfares, effects and Hold music present; every media file re-hashed against the cloud's manifest (or the last push or pull).
  - Laptop: the audio output (Bluetooth and AirPlay fail), the projector (a separate display; mirrored fails with `--laptop-only`), macOS «Reduce motion» off (WARN when on: the projector's drum would spin in its calm mode, unlike the phones'), system and display sleep, power, the clock against time.apple.com (the doors cues count down by it, D203: WARN past 2 s, FAIL past a minute), disk, the show's Chrome flags (no background throttling: FAIL; autoplay: WARN), the Chrome profiles of the show and the laptop's console (WARN in /tmp or the user's temporary folder, which a restart empties, in the everyday profile, or with no laptop console when the tablet is used), and the show's build (`apps/show/dist` must have been built from the sources checked out, by its build stamp; otherwise FAIL, with the fix: rebuild, then restart the relay).
  - Network: the relay and its repertoire; the show page and a console connected; the Wii remote (connected, battery, drops in the last 10 minutes: it warns from 2, a remote at the edge of its range); the show page's audio clock (D284: FAIL while its state says `audioStalled`, the drum and the Shuffle frozen, with the runbook's fix; only with a show page sending state); the console's LAN address answering (optional with `--laptop-only`, when the tech drives from the laptop without the tablet).
  - Cloud: reachable; the laptop token signs in, with round trip and clock offset; the link's status file fresh and in sync; the Game and edition; the Game plan, with printed cards of every round's card type; each card type's price; every round on a printed side whose pool has songs (WARN for a printed side no round plays, D178).
  It never connects as a second laptop: the link writes `data/link/status.json` every 5 s for it.
- **The Game plan** is all public (rounds, prizes, sponsors, schedule), so it lives in the public state. Saving it sends one change to every phone and a `cloud.plan` to the laptop, which also gets it on every hello. Logos are files under `/media/`, never data URLs in the plan, so a phone's snapshot stays small.
- **A silent laptop** (nothing for 50 s) is marked offline by an alarm. Phones show "Connexió perduda" after 20 s of `link.online === false`.
- **Clocks.** Every link message carries the laptop's clock; the GameRoom keeps the smallest (receive − send) as the offset. The feed's times are on the cloud's clock, and every message carries `nowMs` for the phones.
- **Access** ([`src/access.ts`](src/access.ts), adapted from coin-reader's `requireAccess`) is checked once in the Worker, before the GameRoom. It accepts multiple AUDs and fails closed. People pass on admin routes when their email is on `CF_ACCESS_EMAILS` or under `CF_ACCESS_EMAIL_DOMAIN`. The laptop's service token passes on `/ws/show` when its client ID is in `CF_ACCESS_SERVICE_TOKENS`. `ACCESS_DEV=true` only works on localhost.
- **Free plan.** Phones send nothing; there are no heartbeats except the laptop's, one snapshot row, and static files that never run the Worker. The [load test](reports/) puts a pessimistic show night at about half the daily request quota.

Every tunable is in [`src/config.ts`](src/config.ts); the phones' own are `PUBLIC_FEED` in `packages/protocol/public.ts`. Deployment, secrets and dashboard steps: [docs/deploy-plan.md](docs/deploy-plan.md). Where Platform's work stands and what comes next: [docs/HANDOFF.md](docs/HANDOFF.md).
